# תיעוד API

Base URL: `https://app.yeda-phone.com`

אימות: הוסף כותרת `Authorization: Token <YOUR_API_TOKEN>` לכל בקשה.

## מפת האובייקטים במערכת

המערכת מנהלת **מוסד** אחד פעיל לכל משתמש API. כל הקריאות פועלות על המוסד שאליו משויך הטוקן.

| אובייקט | מה זה | קטגוריה בתיעוד |
|---|---|---|
| מערכת (מוסד) | המוסד הפעיל: שם, קו טלפון, יתרת יחידות, סוגי השלוחות הקיימים | ניהול מערכות |
| משתמש | אדם ברשימת המשתמשים של המוסד: שם, טלפונים, כיתה, עיר, קבוצה, ושדות דינמיים | ניהול משתמשים |
| שלוחה | יחידת פעילות במערכת הטלפונית (IVR), מסוג מסוים עם הגדרות משלה | שלוחות |
| סוג שלוחה | תבנית של שלוחה, כולל סכמת ההגדרות שלה | שלוחות |
| שיוך משתמש לשלוחה | קישור בין משתמש לשלוחה/צינתוק | ניהול משתמשים |
| הקלטה | קובץ קול (streamfile) | הקלטות |
| דוחות וסטטיסטיקות | נתוני שימוש וניתוח משתמשים לפי שדה | סטטיסטיקות משתמשים, דוחות שימוש |

### איך האובייקטים קשורים

- **מוסד** ← מכיל **משתמשים** ו**שלוחות**.
- **שלוחה** היא מסוג מסוים (**סוג שלוחה**), והגדרותיה נקבעות לפי הסכמה של אותו סוג.
- **משתמש** יכול להיות משויך לשלוחות דרך **שיוך משתמש לשלוחה**.
- **טוקן API** שייך למשתמש מסוג API במוסד, ובעזרתו מזדהים בכל קריאה.


## כללים לכל הקריאות

### אימות

כל קריאה (למעט אלו שמסומנות "לא דורש אימות") חייבת לכלול את הכותרת:

```
Authorization: Token <YOUR_API_TOKEN>
```

את הטוקן אפשר לבחור בסרגל "טוקן פעיל" בראש הדף. הדוגמאות בדף מתמלאות בו אוטומטית.

### פורמט התגובה

רוב התגובות עטופות במבנה אחיד:

| שדה | תיאור |
|---|---|
| `status` | `OK` או `ERROR` או `AUTH FAIL` |
| `msg` | הודעה לקריאה אנושית (ריקה בהצלחה) |
| `data` | התוכן עצמו: אובייקט, רשימה או ריק |

> חלק מהאנדפוינטים מחזירים מבנה שונה. מה שמוצג תחת "דוגמת תגובה" באנדפוינט הוא הקובע.

### קודי סטטוס

| קוד | משמעות |
|---|---|
| 200 | הצלחה |
| 401 | אימות נכשל (טוקן חסר או שגוי) |
| 403 | אין הרשאה לפעולה |
| 404 | הפריט לא נמצא |
| 422 | שגיאת ולידציה, פרטי השדות בתוך `data` |
| 500 | שגיאת שרת |

### כללים נוספים

- בקשות עם גוף (`POST`, `PUT`, `PATCH`, `DELETE`) נשלחות כ-JSON עם הכותרת `Content-Type: application/json`.
- פרמטרים בנתיב מסומנים בסוגריים מסולסלים, למשל `/api/users/{pk}/`.
- **מחיקה היא רכה**: פריט שנמחק מסומן כנמחק ולא נעלם מהמסד.
- **ב-PATCH** שדה שלא נשלח נשאר ללא שינוי, אבל שדה שנשלח עם `null` או ערך ריק נדרס. פרטים באנדפוינט עצמו.
- רשימות גדולות מחולקות לעמודים בעזרת `limit` ו-`offset`. ברירות המחדל והמקסימום מצוינים באנדפוינט.
- הכתובת של כל אנדפוינט בדף ניתנת להעתקה כקישור ישיר.


## התחלה מהירה (למפתחים ולסוכני AI)

סדר פעולות מומלץ לחיבור ראשון:

1. **בדיקת חיבור**: `GET /api/user/system/` מחזיר את פרטי המוסד הפעיל. אם זה עובד, הטוקן תקין.
2. **הכרת שדות המשתמש**: `GET /api/users/schema/` מחזיר את השדות והערכים האפשריים של משתמש.
3. **עבודה עם משתמשים**: קריאה ויצירה דרך קטגוריית "ניהול משתמשים".
4. **עבודה עם שלוחות**: קודם `GET /api/sclass-types/` לסוגים הקיימים, ואז הסכמה של הסוג הרצוי.

**לסוכני AI**: אפשר להוריד את כל התיעוד בקובץ Markdown אחד (הכפתור בראש הדף). הקובץ אינו מכיל טוקן אמיתי, ובכל מקום שבו נדרש טוקן מופיע `<YOUR_API_TOKEN>`. יש להחליף אותו בטוקן שלך.

> לפני הרצת `POST`, `PUT`, `PATCH` או `DELETE` מהדף: ההרצה פועלת על נתונים אמיתיים של המוסד.


## API יוצא — שלוחת API

שלוחת API מחברת את השיחה הטלפונית לשרת חיצוני. המערכת שולחת בקשת HTTP
לכתובת שהוגדרה בשלוחה, והתגובה קובעת אילו נתונים לשמור וכיצד להמשיך בשיחה.
אפשר להשתמש בה לבירור יתרה, להצגת תפריט אישי, לקליטת נתונים ולתמלול הודעות.

> **כיוון הקריאה:** בניגוד לאנדפוינטים האחרים בתיעוד, כאן **המערכת פונה לשרת שלכם**.
> יש לפתח אצלכם כתובת לקבלת הבקשות; אין זו מתודה בכתובת ה-API של המערכת,
> ולא ניתן להריץ אותה מטופס ההרצה בתיעוד.
> כללי האימות ומעטפת `status` / `msg` / `data` של ה-API הנכנס אינם חוזה התגובה כאן.
> אם השרת שלכם דורש אימות, הגדירו כותרות מתאימות בשלוחה. טוקן שנבחר בסרגל התיעוד
> אינו מצורף אוטומטית לבקשות היוצאות.

### התחלה מהירה

1. הכינו בשרת שלכם כתובת HTTPS לקבלת בקשות ולהחזרת תשובה ישירה.
2. הגדירו שלוחה מסוג API: כתובת, שיטת HTTP, כותרות ופרמטרים.
3. בחרו מצב פענוח תשובה: `legacy` או `flow`.
4. הגדירו שלוחת המשך; ב-Flow הגדירו גם שלוחה לטיפול בשגיאה או בחריגת לולאה.
5. בצעו שיחת בדיקה ובדקו את הבקשה שהתקבלה ואת הפעולה שבוצעה.

| מצב | מתאים ל | מהלך הפעולה |
|---|---|---|
| `legacy` (ברירת מחדל) | שליחת נתונים וקבלת תשובה אחת | בקשה אחת, שמירת נתונים וניתוב לשלוחה |
| `flow` | שיחה רב-שלבית עם החלטות בזמן אמת | תגובת JSON מגדירה פעולה; פעולה מסוג `api` שולחת בקשה נוספת |

כל שלוחה פועלת במצב אחד. תגובת Legacy אינה מפוענחת כרשימת פעולות Flow.

### הגדרות השלוחה והבקשה הראשונה

| הגדרה | שם טכני | תיאור |
|---|---|---|
| לינק | `url` | כתובת השרת שלכם; אפשר לשלב ערכים דינמיים, למשל `https://example.com/api/balance?tz={תעודת_זהות}` |
| שיטה | `method` | `GET`, `POST` או `POST-FORM`; ברירת המחדל היא `GET` |
| כותרות | `headers` | רשימת זוגות `{key, value}`, למשל כותרת `Authorization` לפי האימות בשרת שלכם |
| פרמטרים | `parameters` | רשימת זוגות `{key, value}`; ערכים דינמיים מוחלפים לפני השליחה |
| סוג פענוח תשובת API | `response_mode` | `legacy` או `flow` |
| שלוחת שאלון לקבלת נתונים | `sclass_form` | שאלון אופציונלי לפני הבקשה הראשונה; תוצאותיו זמינות בזיכרון השיחה |
| האם למחוק את התוצאות בסיום השאלון | `delete_result` | ב-Legacy: מחיקת רשומת תוצאת השאלון אחרי הקריאה, בלי למחוק את הנתונים מזיכרון השיחה |
| שליחת נתונים חלקיים | `save_data_if_hangup` | מאפשרת שליחה של הנתונים שנאספו גם כשהמתקשר ניתק במהלך שאלון הקדם |
| בסיום הפעולה, העבר אל שלוחה | `success_move_to_sclass` | יעד קבוע ב-Legacy; ב-Flow יעד המשך אם הזרימה מסתיימת בלי מעבר מפורש |
| מקסימום קריאות API ברצף | `max_api_loops` | ב-Flow: ברירת מחדל 100, תקרה 400; הבקשה הראשונה נכללת בספירה |
| שלוחה במקרה שגיאה / חריגת לולאה | `error_move_to_sclass` | יעד לטיפול בכשל ב-Flow; הגדירו שלוחת חזרה מתאימה |

> `delete_result` אינו מופעל במסלול Flow הנוכחי. אם נדרשת מחיקת תוצאות השאלון,
> אין להסתמך על הגדרה זו במצב Flow.

| שיטה בהגדרות | הבקשה שנשלחת לשרת שלכם |
|---|---|
| `GET` | פרמטרים ב-query string |
| `POST` | גוף JSON עם `Content-Type: application/json` |
| `POST-FORM` | בקשת `POST` עם שדות `multipart/form-data`; זהו שם מצב שליחה, לא HTTP verb נוסף |

נתוני המתקשר אינם נשלחים אוטומטית במעטפת קבועה. הגדירו במפורש אילו פרמטרים
לשלוח, למשל `caller={זיהוי_שיחה}` ו-`tz={תעודת_זהות}`.
הכתובות תחת `example.com` והערכים בדוגמאות הם להמחשה בלבד.

### Legacy — תשובה אחת ושמירת נתונים

אחרי שאלון הקדם נשלחת בקשה אחת. השרת יכול להחזיר טקסט פשוט או אובייקט JSON:

```json
{
  "customer_name": "ישראל ישראלי",
  "balance": "150.50"
}
```

אין חובה לשדות `status`, `save` או `action` במצב זה. מיפוי השמירה נקבע בשלוחה:

| שדה ב-`save_data` | תיאור |
|---|---|
| `response_key` | שם שדה ברמה העליונה של אובייקט התגובה, למשל `balance`; `*` לשמירת תשובת טקסט בשלמותה |
| `memory_name_save` | שם הערך בזיכרון השיחה, למשל `יתרה`, לשימוש בהמשך כ-`{יתרה}` |
| `user_field` | אופציונלי: `name`, `tz`, `id_mosad` או `class_name` לשמירה בכרטיס המשתמש; `-` ללא שמירה בכרטיס |

> השתמשו באובייקט JSON עם שדות מפורשים. בחירה באמצעות `[0]` או נתיב לשדה מקונן
> אינה נתמכת במיפוי השמירה הנוכחי.
> זיכרון שיחה אינו שמירה קבועה בכרטיס המשתמש; לשמירה קבועה יש לבחור `user_field`.

**סדר הניתוב לאחר התגובה:**

1. אם מוגדר `success_move_to_sclass`, עוברים אליו ללא תלות בתוכן התגובה.
2. אחרת נבדקת `move_to_sclass_options` לפי הסדר. כל שורה מכילה `value` ו-`sclass`;
   הכלל הראשון שמתאים לתגובה קובע את היעד. `*` משמש כלל כללי, ולכן מומלץ להציבו בסוף.

### Flow — מבנה התגובה וניהול המשך השיחה

כל בקשת Flow מצפה לאובייקט JSON. ברמה העליונה מותרים רק `save` ו-`action`:

```json
{
  "save": {
    "שם_לקוח": "ישראל ישראלי",
    "יתרה": "150.50"
  },
  "action": {
    "type": "move",
    "target": "תפריט ראשי"
  }
}
```

| שדה | חובה | תיאור |
|---|---|---|
| `save` | לא | אובייקט מפתח–ערך לשמירה בזיכרון השיחה; אינו מעדכן את כרטיס המשתמש |
| `action` | להמשך הזרימה | אובייקט פעולה עם `type` מוכר |

השמירה מתבצעת לפני הפעולה, ולכן אפשר להשתמש בערכים שנשמרו כבר באותה תגובה.
פעולה מסוג `api` שולחת בקשה נוספת לשרת, שגם היא חייבת להחזיר תגובת Flow.
תפריטים, השמעות ופקודות אינם יוצרים בקשת HTTP אלא אם הוגדרה בהם פעולת `api`.

**סיום ללא פעולה:** אפשר להשמיט `action` או להחזיר `"action": null`.
הזרימה מסתיימת, ואם הוגדר `success_move_to_sclass` עוברים אליו.
`"action": {}` אינו סיום תקין: חסר בו סוג פעולה והוא נדחה.
אין להוסיף שדות עליונים כגון `status`, `msg` או `data`.

### פעולות Flow

| `type` | פעולה |
|---|---|
| `api` | פנייה נוספת לשרת שלכם |
| `menu` | תפריט בחירה |
| `play_list` | השמעת רשימה עם מקשי ניווט |
| `commands` | ביצוע רצף פקודות |
| `move` | מעבר לשלוחה במוסד הנוכחי |
| `hangup` | ניתוק מפורש של השיחה |

#### `api` — בקשה נוספת

```json
{
  "type": "api",
  "url": "https://example.com/api/verify",
  "method": "POST",
  "headers": [
    {"key": "Authorization", "value": "Bearer <YOUR_OUTBOUND_API_KEY>"}
  ],
  "params": [
    {"key": "tz", "value": "{תעודת_זהות}"}
  ]
}
```

| שדה | חובה | ברירת מחדל | תיאור |
|---|---|---|---|
| `url` | כן | — | כתובת HTTPS ציבורית |
| `method` | לא | `GET` | `GET`, `POST` או `POST-FORM` |
| `headers` | לא | `[]` | רשימת `{key, value}` של כותרות הבקשה |
| `params` | לא | `{}` | רשימת `{key, value}` או אובייקט מפתח–ערך; הערכים נשלחים כמחרוזות |

בפעולת Flow השדה נקרא `params`; בהגדרות הבקשה הראשונה הוא נקרא `parameters`.
כל בקשה מגדירה את הנתונים ואת כותרות האימות שלה; אין להסתמך על ירושה
אוטומטית מהבקשה הראשונה.

#### `menu` — תפריט בחירה

```json
{
  "type": "menu",
  "title": "לבירור יתרה הקישו 1, לשיחה עם נציג הקישו 2",
  "items": [
    {"key": "1", "api": {"url": "https://example.com/api/balance", "method": "GET"}},
    {"key": "2", "move_to": "נציג שירות"},
    {"key": "*", "hangup": true}
  ],
  "default_action": {"type": "move", "target": "תפריט ראשי"}
}
```

| שדה | חובה | תיאור |
|---|---|---|
| `title` | לא | טקסט פתיחה או שם קובץ להשמעה; תומך בערכים דינמיים |
| `menu_audio` | לא | קובץ תפריט נוסף; מושמע אם לא נקלטה בחירה במהלך `title` |
| `items` | כן | עד 20 אפשרויות, עם `key` של תו אחד לכל אפשרות |
| `default_action` | לא | פעולה אם לא נמצאה בחירה מתאימה; ללא פעולה הזרימה מסתיימת |

בכל פריט הגדירו `key` ו**אפשרות המשך אחת**:

| שדה בפריט | תיאור |
|---|---|
| `api` | אובייקט בקשה כמו בפעולת `api`, ללא צורך ב-`type` |
| `play_list` | רשימת פריטי השמעה או אובייקט הגדרות של רשימת השמעה |
| `move_to` | שם או נתיב של שלוחת היעד |
| `hangup` | `true` לניתוק מפורש |
| `action` | אובייקט פעולה מלא, למשל `commands` |

#### `play_list` — רשימת השמעה

```json
{
  "type": "play_list",
  "items": [
    {"type": "text", "value": "שלום {שם}"},
    {"type": "audio", "value": "תודה_שהתקשרתם"},
    {"type": "number", "value": "{יתרה}"},
    {"type": "shekel", "value": "{סכום}"}
  ],
  "keys": {"next": "8", "prev": "2", "back": "*"},
  "back_action": {"type": "move", "target": "תפריט ראשי"},
  "next_action": {"type": "move", "target": "תפריט ראשי"}
}
```

| שדה | חובה | תיאור |
|---|---|---|
| `items` | כן | עד 100 פריטים, לפי סדר ההשמעה |
| `keys` | לא | מקשי ניווט: `next=8`, `prev=2`, `back=*` כברירת מחדל |
| `back_action` | לא | פעולה בלחיצה על מקש החזרה |
| `next_action` | לא | פעולה לאחר סיום הרשימה |

| סוג פריט | `value` | שדות נוספים |
|---|---|---|
| `text` | טקסט להקראה | ערכים דינמיים נתמכים |

### פקודות בתוך `commands`

כל פקודה כוללת `cmd`. בפקודות שמחזירות קלט, `save_as` הוא שם אופציונלי
לשמירת התוצאה בזיכרון השיחה. `value` ו-`prompt_audio` יכולים לכלול ערכים דינמיים.
`escape_digits` מגדיר מקשים להפסקת השמעה; ברירת המחדל היא מחרוזת ריקה.
זמני ההמתנה וההקלטה להלן נמדדים במילישניות.

### ערכים דינמיים וזיכרון השיחה

אפשר לשלב `{שם_ערך}` בכתובת, בערכי פרמטרים ובטקסטים התומכים בכך.
הערך מוחלף מתוך זיכרון השיחה לפני הביצוע.

| Placeholder | תיאור |
|---|---|
| `{זיהוי_שיחה}` | מספר הטלפון המתקשר |
| `{מספר_שחוייג}` | המספר שאליו חויג |
| `{שם}` | שם המשתמש הרשום |
| `{תעודת_זהות}` | תעודת הזהות הרשומה |
| `{קוד_אישי}` | הקוד האישי במוסד |
| `{כיתה_במוסד}` | הכיתה הרשומה |
| `{מזהה_שיחה}` | מזהה רשומת השיחה במערכת |

ערכי המשתמש תלויים במידע הרשום. ערך חסר מוחלף במחרוזת ריקה.
השתמשו בשם פשוט בלבד: אותיות, ספרות, עברית, רווחים וקו תחתון.
גישה כגון `{customer.name}` או `{items[0]}` אינה נתמכת.

נתונים שנשמרו ב-`save`, ב-`save_as` או ב-`memory_name_save` זמינים בשלבים הבאים
באותה שיחה. הם נשמרים במרחב שמות עם קידומת `api_`:
`"save": {"יתרה": "150.50"}` מאפשר שימוש ב-`{יתרה}` וגם ב-`{api_יתרה}`.
אם כבר קיים ערך מערכתי בשם הלא-מקודם, הוא מקבל קדימות;
השתמשו בקידומת המפורשת כדי לקרוא את ערך ה-API ללא התנגשות.

| מגבלת שמירה ב-Flow | ערך |
|---|---|
| מספר פריטים ב-`save` | עד 50 |
| אורך שם לשמירה | 1–64 תווים |
| אורך ערך טקסט לשמירה | עד 4096 תווים |
| עומק מבנה לשמירה | עד 2 |
| שמות מערכת מוגנים | אין לדרוס שמות כגון `school`, `user`, `permissions`, `password` או `token`, גם עם קידומת `api_` |

### דיווח אירועים ושגיאות לשרת שלכם

ב-Flow ניתן להגדיר כתובת דיווח נפרדת מהכתובת שמנהלת את השיחה.
הדיווח אינו בקשה לצעד Flow נוסף, ואינו מחליף את `error_move_to_sclass`.

| הגדרה | שם טכני | תיאור |
|---|---|---|
| שליחת דיווח שגיאות ל-API ייעודי | `error_report_api_enabled` | הפעלת הדיווח; ברירת מחדל `false` |
| דיווח גם בעת ניתוק שיחה | `error_report_on_hangup` | דיווח `call_hangup`; דורש שגם הדיווח הכללי יהיה פעיל |
| כתובת API לדיווח שגיאות | `error_report_api_url` | כתובת HTTPS ציבורית |
| שיטת שליחת דיווח שגיאות | `error_report_api_method` | ברירת מחדל `POST`; גם `GET` ו-`POST-FORM` נתמכות |
| כותרות לדיווח שגיאות | `error_report_api_headers` | רשימת `{key, value}`, כולל אימות לפי הצורך |
| פרמטרים קבועים לדיווח שגיאות | `error_report_api_parameters` | זוגות `{key, value}` שמתווספים לדיווח; אינם יכולים לדרוס שדות מערכת |

```json
{
  "event": "api_error",
  "error_code": "http_call_failed",
  "message": "API call failed",
  "sclass_id": "1234",
  "school_id": "5",
  "response_mode": "flow",
  "action_type": "api",
  "request_url_host": "example.com",
  "response_status": "",
  "caller_id_masked": "052*******",
  "call_id": "example-channel-id",
  "timestamp": "2026-01-01T10:00:00+02:00",
  "extra": {}
}
```

| שדה | תיאור |
|---|---|
| `event` | סוג האירוע, `api_error` |
| `error_code` | קוד לאבחון; העדיפו אותו על פענוח טקסט ההודעה |
| `message` | הודעת אבחון מקוצרת |
| `sclass_id` / `school_id` | מזהי השלוחה והמוסד כמחרוזות |
| `response_mode` | מצב העבודה |
| `action_type` | הפעולה שבמהלכה דווח האירוע; עשוי להיות ריק |
| `request_url_host` | שם ה-host בלבד, ללא כתובת מלאה; עשוי להיות ריק |
| `response_status` | קוד HTTP כמחרוזת אם זמין; אחרת `""` |
| `caller_id_masked` | זיהוי מתקשר ממוסך |
| `call_id` | מזהה ערוץ השיחה; אינו בהכרח הערך המספרי של `{מזהה_שיחה}` |
| `timestamp` | זמן האירוע בפורמט ISO 8601 |
| `extra` | נתוני אבחון מסוננים; בדיווח ניתוק עשויים להיכלל ערכים שנאספו בשיחה |

כותרות הבקשה ותוכן התגובה המלא אינם מצורפים לדיווח. שמות רגישים מסוננים,
אך הסינון אינו תחליף למדיניות פרטיות: אין לאסוף סודות בזיכרון השיחה,
ויש להביא בחשבון שדיווח ניתוק עשוי לכלול נתונים אישיים שנאספו.
כשל בשליחת הדיווח אינו יוצר דיווח חוזר לאותה כתובת.

| `error_code` | משמעות |
|---|---|
| `flow_security_error` | תגובה או פעולה נדחתה בבדיקת המבנה או האבטחה |
| `max_api_loops_exceeded` | חריגה ממספר בקשות ה-API המותר |
| `max_action_steps_exceeded` | חריגה מתקרת כלל צעדי הזרימה, גם ללא בקשות HTTP רבות |
| `outbound_url_rejected` | כתובת יוצאת נדחתה |
| `http_method_not_allowed` | שיטת שליחה לא נתמכת |
| `http_call_failed` | כשל בפנייה לשרת |
| `response_too_large` | תגובה גדולה מהמגבלה |
| `invalid_flow_response` | תגובה שאינה עומדת בחוזה Flow |
| `register_zintok_invalid_sclass` | שלוחת רישום לא נמצאה או אינה מורשית |
| `register_zintok_failed` | כשל ברישום או בהסרה מצינתוק |
| `record_stt_failed` | כשל בהקלטה או בזיהוי דיבור |
| `press_nums_en_letters_failed` | כשל בקליטת טקסט במקשים |
| `gemini_stt_failed` | כשל בהקלטה או בתמלול Gemini |
| `action_commands_error` | כשל בביצוע רצף פקודות |
| `handle_action_error` | כשל בטיפול בפעולה |
| `legacy_exec_error` / `exec_error` | כשל כללי בביצוע השלוחה |
| `call_hangup` | ניתוק מצד המתקשר; נשלח רק אם הופעל דיווח ניתוק, ואינו מעיד כשלעצמו על תקלה |

### מגבלות ותכנון אמין

ההגנות הבאות מיושמות במסלול **Flow** ובכתובת הדיווח.
השתמשו ב-HTTPS ובכתובות ציבוריות גם ב-Legacy, אך אין להניח שהמסלול הישן
אוכף את כל ההגנות והמגבלות של Flow.

| נושא | מגבלה ב-Flow |
|---|---|
| פרוטוקול ויעד | HTTPS ציבורי בלבד; כתובות מקומיות, פרטיות ויעדי metadata נחסמים |
| מבנה כתובת | ללא `user:pass@host` וללא fragment מסוג `#...` |
| הפניות HTTP | אין מעקב אוטומטי אחרי 3xx; החזירו תשובה ישירה, מומלץ `200` |
| שיטות שליחה | `GET`, `POST`, `POST-FORM` |
| זמני HTTP | חיבור: 5 שניות; קריאה: 15 שניות |
| גודל תגובה | שמרו תגובות מתחת ל-1MB; אין להסתמך על בדיקת הגודל כהגנה על כל אובייקט JSON |
| אורך טקסט לפעולה | עד 4096 תווים; טקסטים עשויים להיחתך |
| פקודות ברצף | עד 20 |
| אפשרויות בתפריט | עד 20 |
| פריטים ברשימת השמעה | עד 100 |
| עומק קינון פעולות | עד 8 |
| בקשות API בשיחה | לפי `max_api_loops`, ברירת מחדל 100 ותקרה 400 |
| כלל צעדי הזרימה | תקרה פנימית של 2000 |

גם כותרות עוברות בדיקה. אין לשלוח כותרות כגון `Host`, `Content-Length`,
`Cookie`, `Connection` או `X-Forwarded-For` דרך הגדרות ה-API.
שלוחת מעבר ושלוחת רישום חייבות להיות מורשות במוסד הנוכחי.

מכסת בקשות ה-API כוללת את הבקשה הראשונה וכל פעולת `api` נוספת.
פעולות `menu`, `commands` ו-`play_list` אינן צורכות מכסה זו,
אך נכללות בתקרת הצעדים הכללית. הימנעו מפעולות שמפנות לעצמן ללא תנאי סיום.
אל תבנו על ניסיון HTTP חוזר אוטומטי; תכננו טיפול בכשל ושלוחת חזרה.

### דוגמאות מקצה לקצה

#### Legacy — בירור יתרה והעברתה לשלוחת השמעה

הגדירו `response_mode=legacy`, כתובת `https://example.com/api/balance`,
שיטה `POST`, ופרמטר `tz` שערכו `{תעודת_זהות}`.
ב-`save_data` הגדירו `response_key=balance`, `memory_name_save=יתרה` ו-`user_field=-`.
הגדירו `success_move_to_sclass` לשלוחת „השמעת יתרה”.

הבקשה לשרת שלכם:

```http
POST /api/balance HTTP/1.1
Host: example.com
Content-Type: application/json

{"tz": "123456789"}
```

תגובת השרת:

```json
{"balance": "150.50"}
```

המערכת שומרת את היתרה בזיכרון השיחה ועוברת לשלוחת ההשמעה,
שבה ניתן להשתמש ב-`{יתרה}`.

#### Flow — תפריט שירות ובירור יתרה

הגדירו `response_mode=flow`, כתובת `https://example.com/api/start`, שיטה `POST`,
ופרמטר `caller` שערכו `{זיהוי_שיחה}`. הגדירו שלוחת המשך ושלוחת שגיאה.
השרת מקבל `{"caller": "0521234567"}` ומחזיר:

```json
{
  "save": {"שם_לקוח": "ישראל ישראלי"},
  "action": {
    "type": "menu",
    "title": "שלום {שם_לקוח}, לבירור יתרה הקישו 1, לשיחה עם נציג הקישו 2",
    "items": [
      {
        "key": "1",
        "api": {
          "url": "https://example.com/api/balance",
          "method": "POST",
          "params": [{"key": "caller", "value": "{זיהוי_שיחה}"}]
        }
      },
      {"key": "2", "move_to": "נציג שירות"},
      {"key": "*", "move_to": "תפריט ראשי"}
    ],
    "default_action": {"type": "move", "target": "תפריט ראשי"}
  }
}
```

לחיצה על `1` יוצרת בקשת `POST` לבירור יתרה, עם מספר המתקשר.
אם השרת דורש אימות, הוסיפו `headers` גם לפעולת הבקשה הזו.
התגובה לבירור:

```json
{
  "save": {"יתרה": "150.50"},
  "action": {
    "type": "play_list",
    "items": [
      {"type": "text", "value": "היתרה שלכם היא"},
      {"type": "shekel", "value": "{יתרה}"}
    ],
    "back_action": {"type": "move", "target": "תפריט ראשי"},
    "next_action": {"type": "move", "target": "תפריט ראשי"}
  }
}
```

המערכת משמיעה את הסכום ומחזירה את המתקשר לתפריט הראשי.

#### Flow — תמלול פנייה ושליחתה לשרת

בתגובה לבקשת הפתיחה החזירו:

```json
{
  "action": {
    "type": "commands",
    "commands": [
      {
        "cmd": "gemini_stt",
        "prompt_audio": "ספרו כיצד נוכל לעזור לאחר הצליל",
        "language": "he",
        "say_stt": true,
        "save_as": "פניית_לקוח"
      }
    ],
    "next_action": {
      "type": "api",
      "url": "https://example.com/api/submit-request",
      "method": "POST",
      "params": [
        {"key": "caller", "value": "{זיהוי_שיחה}"},
        {"key": "text", "value": "{פניית_לקוח}"}
      ]
    }
  }
}
```

אחרי התמלול נשלחת בקשה עם `caller` ו-`text`.
השרת צריך לבדוק שהתמלול אינו ריק לפני יצירת פנייה או החזרת הודעת הצלחה.
גם תגובת `submit-request` חייבת לעמוד בחוזה Flow, למשל:

```json
{"action": {"type": "move", "target": "תפריט ראשי"}}
```

מה מקבלים בתשובה:

### העלאת קבצי PDF

**Method:** `POST`

**URL:** `https://app.yeda-phone.com/api/upload_files/`

**דורש אימות:** כן

מעלה קובץ PDF למערכת, לשלוחה מסוג "הזמנת מסמכים לפקס", לצורך שליחה מאוחרת של המסמך כפקס.

מה מקבלים בתשובה:
הודעת אישור טקסטואלית הכוללת את שם הקובץ, מזהה הקובץ בתוך השלוחה, והנתיב שאליו הועלה.

מתי משתמשים בזה:
לפני שליחת מסמך כפקס יש להעלות אותו תחילה דרך קריאה זו - בדרך כלל כהכנה לקריאה ל"שליחת מסמך קיים  מערכת כפקס". 
ניתן לשלוח את הקובץ כקובץ מצורף רגיל (multipart/form-data) או כטקסט מקודד Base64 בתוך גוף JSON.

חשוב לדעת:
השלוחה המצוינת בנתיב חייבת להיות מוגדרת מראש כשלוחה מסוג "הזמנת מסמכים לפקס", אחרת הבקשה נכשלת. יש להעלות קובץ בפורמט PDF בלבד - קובץ שאינו PDF יישמר במערכת אך לא יומר אוטומטית לפורמט המתאים לשליחה פקס, ולכן לא ניתן יהיה לשלוח אותו בהמשך. אם לא מצוין קוד מסמך, המערכת מקצה לו אוטומטית מספר רץ בתוך השלוחה; אם מצוין קוד שכבר קיים באותה שלוחה, הקובץ הקיים יוחלף בקובץ החדש באותו קוד במקום ליצור רשומה   נוספת. כאשר הקובץ נשלח כטקסט מקודד Base64, יש לציין גם את שם הקובץ.

**פרמטרים**

| שם | מיקום | סוג | חובה | ברירת מחדל | תיאור |
|---|---|---|---|---|---|
| `path` | - | string | כן | - | הנתיב של השלוחה שאליה מועלה הקובץ; חייבת להיות מוגדרת כשלוחת מסמכים לפקס |
| `file` | - | file | כן | - | קובץ ה-PDF להעלאה; כקובץ מצורף (multipart) או כטקסט Base64 בבקשת JSON |
| `file_name` | - | string | לא | - | שם הקובץ; חובה כאשר הקובץ נשלח כטקסט Base64, אחרת מושלם אוטומטית משם הקובץ המקורי |
| `number` | - | string | לא | - | קוד מספרי (ספרות בלבד) לזיהוי הקובץ בשלוחה; אם לא צוין, מוקצה אוטומטית |

**cURL**

```bash
curl -X POST "https://app.yeda-phone.com/api/upload_files/" -H "Authorization: Token <YOUR_API_TOKEN>" -H "Accept: application/json"
```

**דוגמת תגובה**

```json
{
  "message": "File חוזה שכירות 2026 saved successfully with id 842 at מסמכים/חוזים"
}
```

### שליחת מסמך קיים במערכת כפקס

**Method:** `POST`

**URL:** `https://app.yeda-phone.com/api/send_fax_api/`

**דורש אימות:** כן

שולח כפקס מסמך שהועלה מראש למערכת, ללא צורך בהדפסה או בהזנה ידנית למכשיר הפקס.

מה מקבלים בתשובה:
הודעת אישור שהבקשה התקבלה ונכנסה לתהליך שליחה.

מתי משתמשים בזה:
לאחר שמסמך כבר הועלה לשלוחת מסמכים לפקס (ראו "העלאת קבצי PDF"), ניתן להשתמש בקריאה זו כדי לשלוח אותו כפקס למספר יעד, מבלי לטעון מחדש את הקובץ עצמו.

חשוב לדעת:
יש לזהות את המסמך לפי שם או לפי קוד/מספור - לפחות אחד מהשניים חובה.
השליחה מתבצעת ברקע ולא מיידית עם קבלת הבקשה, והפקס נשלח בפועל תוך דקות ספורות. אם המסמך לא הועלה בפורמט PDF, או שלא נמצא בפועל בשלוחה, השליחה נכשלת.

**פרמטרים**

| שם | מיקום | סוג | חובה | ברירת מחדל | תיאור |
|---|---|---|---|---|---|
| `path` | - | string | כן | - | הנתיב של השלוחה שבה שמור המסמך |
| `name` | - | string | לא | - | שם המסמך כפי שמופיע במערכת; יש לספק שם או קוד מסמך |
| `numeration` | - | string | לא | - | הקוד שהוקצה למסמך בעת ההעלאה; ניתן לספק במקום שם המסמך |
| `fax_number` | - | string | כן | - | מספר הפקס של היעד, כולל קידומת |
| `skip_from` | - | boolean | לא | - | דילוג על כותרת שם השולח בעמוד הראשון; ברירת מחדל: מוצגת |
| `resolution` | - | select | לא | normal | איכות ההדפסה של המסמך הנשלח; ברירת מחדל: רגיל (ערכים אפשריים: `low`, `normal`, `high`) |

**cURL**

```bash
curl -X POST "https://app.yeda-phone.com/api/send_fax_api/" -H "Authorization: Token <YOUR_API_TOKEN>" -H "Accept: application/json"
```

**דוגמת תגובה**

```json
{
  "status": "OK",
  "message": "Fax will send in a few minutes"
}
```
