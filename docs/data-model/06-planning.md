# 06 · מודול התכנון: טיוטות, הערות, דוחות פערים ומיפוי קיים→עתידי

> סטטוס: **טיוטה לדיון**.
> מבוסס על D-006, D-008, D-009, D-011, D-012, D-013, D-016, D-104, D-105 ו-D-108.
> סימון ⚠️ = הנחה שצריך לאמת.

## 1. התפקיד של המודול

- **מודול צדדי (D-105).** הוא קורא את העץ הנוכחי ואת יומן ההאזנות, ולא משנה אותם.
- הוא מחזיק את **העץ העתידי** כטיוטה, את ההערות עליו, ואת **המיפוי מהעץ הקיים אל העתידי**.
- **המיפוי הוא הנכס שמשמר את ההיסטוריה ביום המעבר.** לכן המודול לא נמחק כשמרוקנים את העץ (D-105).

## 2. מה לומדים מהטיוטה מ-21.10

| תופעה בטיוטה | השלכה על המודל |
|---|---|
| הצבע מסמן סטטוס: שחור קיימת, מג'נטה חדשה, כחול דורשת בנייה מיוחדת, אדום הערה או שאלה, כתום הערת בנייה | סטטוס לכל צומת, וסוג לכל הערה. הצבע נשמר רק כמקור |
| המספרים מוצגים הפוך, ובלי `1.` בהתחלה | המספר הגולמי נשמר כפי שנכתב. הנתיב המלא מחושב |
| צמתים בלי מספר ("סיורים וירטואליים") | מספר הוא שדה אופציונלי. הסדר נשמר לפי המיקום במסמך |
| מספור יחסי ("1. טיפים" תחת `1.6.1.1`) | שומרים את הספרה המקומית, והנתיב מחושב מהאב |
| צמתים ריקים ("9.4.") | צומת בלי שם מקבל דגל לבדיקה |
| מידע בתוך הטקסט: מרצה בסוגריים, "64 פרקים", "מתחדשת מדי ___", "סדרה סגורה" | חילוץ אוטומטי להצעות מאפיינים (D-015). לא מאפיין סופי |
| הפניות בטקסט: "יועתקו גם ל-310", "להרשמה מועבר ל-90" | הצעות לקישורים (`extension_link`) ולהגדרות שצריך לכתוב בעתיד |
| הערות בכמה רמות: כל הקו, ענף ראשי, צומת, "שאלות שנותרו" | הערה מוצמדת לטיוטה, לצומת, או לטיוטה כולה |

## 3. ישויות

### 3.1 תכנית וטיוטות

**`migration_plan`** · תכנית מעבר. בשלב הראשון כנראה תהיה רק אחת.
`plan_id`, `name`, `status` (`drafting` / `migrating` / `done`), `created_by`, `created_at`.

**`base_tree_snapshot`** · עותק קפוא של העץ הקיים שהתכנית נשענת עליו.
- נלקח מ-`extension` ברגע שמתחילים את התכנית, ומתעדכן לפני המעבר.
- **לא נמחק כשמרוקנים את העץ.** אחרי הריקון אין דרך אחרת לדעת איזה נתיב ישן שייך לאיזו שלוחה ישנה. זה מה שמאפשר את השיוך מחדש של D-105.
- השדות: `snapshot_id`, `taken_at`, ולכל שלוחה `sclass_id`, `path`, `name`, `cls_type`, `parent_sclass_id`.

**`draft`** · גרסה של טיוטת העץ העתידי.

לפי D-108 יש **טיוטת עבודה אחת** (`working`) לכל תכנית. כולם עורכים אותה, והמיפוי מצביע רק עליה.
- **קובץ שמועלה** הופך לגרסה מסוג `imported`. משווים אותה לטיוטת העבודה, ומאמצים ממנה שינויים צומת אחר צומת או בבת אחת.
- **גרסאות `snapshot`** נשמרות בכל שמירה משמעותית ולפני כל אימוץ, ומשמשות להשוואה ולשחזור.
| שדה | תיאור |
|---|---|
| `draft_id`, `plan_id` | |
| `kind` | `working` (העותק שנערך בעורך) / `snapshot` (גרסה קפואה) / `imported` (מקובץ שהועלה) |
| `source_file_id` | אם הגרסה יובאה מקובץ |
| `based_on_draft_id` | הגרסה הקודמת, להשוואה |
| `created_by`, `created_at`, `label` | למשל "הצעת סידור פנימי 21/10" |

**`draft_node`** · צומת בטיוטה
| שדה | תיאור |
|---|---|
| `node_id` | מזהה פנימי. **נשמר בין גרסאות** של אותה טיוטה, כדי שהערות ומיפוי לא יתנתקו. בקובץ שמועלה, צמתים מותאמים לצמתי טיוטת העבודה לפי מיקום ושם, ומקבלים את ה-`node_id` שלהם |
| `draft_id`, `parent_node_id`, `position` | מיקום במסמך |
| `digit` | הספרה המקומית (`1`, `7`, `90`, `999`). ריק אם הצומת בלי מספר |
| `full_path` | נתיב מלא מחושב (`1.1.1`). ריק אם לאחד האבות אין ספרה |
| `raw_number_text`, `raw_text` | בדיוק כפי שנכתבו בקובץ |
| `title` | שם |
| `node_status` | `existing` / `new` / `new_special_build` / `unknown` |
| `node_kind` | `extension` / `heading` (כותרת בלי שלוחה, כמו "תכני אור עולם שאינם קשורים...") / `placeholder` (ריק או "???") |
| `planned_cls_type` | סוג שלוחה מתוכנן, אם ידוע |
| `hints` | JSON של מה שחולץ מהטקסט: מרצים, מספר פרקים, תדירות, "סדרה סגורה", הפניות ("ל-310") |
| `source_span` | מיקום בקובץ המקור (עמוד ושורה), לתצוגה ולדוח פערים |

**`draft_note`** · הערה
| שדה | תיאור |
|---|---|
| `note_id`, `draft_id`, `node_id` | `node_id` ריק אם ההערה על כל הטיוטה |
| `scope` | `global` / `section` / `node` / `open_question` |
| `note_kind` | `question` (אדום) / `build_note` (כתום) / `comment` (נכתבה במערכת) |
| `text`, `source_color` | |
| `status` | `open` / `resolved` / `wont_do` |
| `author`, `created_at`, `resolved_by`, `resolved_at` | |
| `parent_note_id` | שרשור תגובות בתוך המערכת |

### 3.2 העלאת קובץ ודוח פערים (D-009)

**`uploaded_file`** · `file_id`, `filename`, `format` (`docx` / `gdoc` / `html` / `pdf` / `txt`), `uploaded_by`, `uploaded_at`, `sha256`, `parse_status`, `parse_log`.
הקובץ המקורי נשמר.

**`gap_report`** · `report_id`, `draft_id` (מה נבדק), `compared_to` (`draft:<id>` / `current_tree` / `base_snapshot`), `created_at`.

**`gap_item`** · פריט בדוח
| `gap_kind` | דוגמה |
|---|---|
| `added` / `removed` | צומת חדש בטיוטה / צומת שנמחק |
| `renamed` | אותו מיקום, שם אחר |
| `moved` | אותו צומת (לפי `node_id` או לפי התאמה), מיקום אחר |
| `number_conflict` | שני צמתים עם אותה ספרה תחת אותו אב |
| `unnumbered` | צומת בלי ספרה |
| `existing_not_found` | צומת שמסומן "קיים" (שחור), אבל לא נמצאה לו שלוחה בעץ |
| `current_not_planned` | שלוחה בעץ הנוכחי שלא מופיעה בטיוטה ולא מופתה. כולל מספר ההאזנות שלה |
| `pattern_deviation` | חריגה מהדפוס 1/7/8/9/0 (D-016) |
| `ref_needs_rewrite` | הפניה ב-`settings` לנתיב שישתנה (נגזר מ-`extension_setting_ref`) |
| `open_note` | הערה פתוחה מסוג שאלה |

לכל פריט נשמרים `gap_kind`, `severity`, `draft_node_id`, `sclass_id`, `detail` ו-`status` (`open` / `accepted` / `fixed`).

### 3.3 מיפוי קיים→עתידי (D-006, D-008, D-011, D-013)

**`mapping_row`** · שורת מיפוי
| שדה | תיאור |
|---|---|
| `mapping_id`, `plan_id` | |
| `relation` | `keep` (נשאר במקום) / `move` (אותו `id`, מיקום חדש) / `rebuild` (שלוחה חדשה במקום הישנה) / `merge` (כמה→אחת) / `split` (אחת→כמה) / `retire` (נסגרת) |
| `sources[]` | `sclass_id` ישנים, עם הנתיב והשם מתוך `base_tree_snapshot` |
| `targets[]` | `node_id` בטיוטה. אחרי הבנייה בידע פון נוסף גם `new_sclass_id` |
| `effective_from` | תאריך תחילת תוקף (D-011) |
| `confidence` | 0–1 |
| `signals` | JSON: דמיון שם, מרצה משותף, סוג, הקלטות משותפות, אותו `id` (D-008) |
| `status` | `suggested` / `needs_decision` (מתחת לסף) / `approved` / `rejected` |
| `decided_by`, `decided_at`, `note` | |

**`split_rule`** · בפיצול, ההיסטוריה עוברת יחד עם השיעור (D-013).
`mapping_id`, `lesson_id`, `target_node_id`. ⚠️ תלוי במודל השיעורים (מסמך 02). עד אז, פיצול נשמר בלי כללים, ומסומן "דורש שיוך שיעורים".

**`branch_status`** · סטטוס מעבר לכל ענף (D-011)
`plan_id`, `node_id` (ראש הענף בטיוטה), `status` (`planned` / `in_progress` / `moved` / `verified`), `changed_by`, `changed_at`, `note`.
ענף בלי סטטוס משלו יורש את הסטטוס של הענף שמעליו.

**`new_tree_binding`** · אחרי שהענף נבנה בידע פון, כל צומת בטיוטה נקשר לשלוחה האמיתית שנוצרה.
`node_id`, `new_sclass_id`, `method` (`auto_path_name` / `manual`), `confirmed_by`.
זה הבסיס להשוואה בין העץ בפועל לטיוטה אחרי המעבר (D-012).

### 3.4 מדדים ובדיקות (D-012)

**`plan_coverage`** · טבלה נגזרת. איזה חלק מההאזנות ההיסטוריות "ממשיך" לעץ החדש.
`plan_id`, `computed_at`, `period`, `listens_total`, `listens_mapped`, `listens_retired`, `listens_unmapped`, עם פירוט לפי ענף.

**`plan_preview_stats`** · תצוגה מקדימה של סטטיסטיקה על העץ העתידי. טבלאות הסיכום (מסמך 09) מגולגלות דרך המיפוי אל צומתי הטיוטה.

**`validation_rule`** ו-**`validation_result`** · בדיקות תקינות
- הכללים מנוהלים בקטלוג: דפוס 1/7/8/9/0, ספרה כפולה, צומת ריק, הפניה שבורה ב-`settings`, שלוחה קיימת שלא מופתה, ענף בלי מרצה.
- התוצאה נשמרת לכל טיוטה או עץ: `rule_id`, `target`, `severity`, `message`.

## 4. יום המעבר (D-105)

1. **מקפיאים** את `base_tree_snapshot` ואת המיפוי המאושר.
2. **מוחקים** את העץ הנוכחי ואת טבלאות הסיכום, ומייבאים את העץ החדש מידע פון.
3. **קושרים** כל צומת בטיוטה לשלוחה החדשה (`new_tree_binding`).
4. **משייכים מחדש** את כל ההאזנות הישנות בשלושה צעדים:
   1. הנתיב הישן נתרגם לשלוחה ישנה, לפי `base_tree_snapshot`.
   2. השלוחה הישנה נתרגמת לצומת בטיוטה, לפי `mapping_row` (ובפיצול לפי `split_rule`).
   3. הצומת נתרגם לשלוחה החדשה, לפי `new_tree_binding`.
5. **מחשבים מחדש** את טבלאות הסיכום.
6. **מה שלא משויך** עובר לרשימת "לא משויך". `retire` נספר כהיסטוריה של שלוחה שנסגרה.

## 5. נקודות פתוחות

- ⚠️ קריאת צבעים: אפשרית מ-docx, מ-Google Docs ומ-HTML. לא אפשרית מ-PDF. בטיוטה מ-21.10 גם הסדר של הספרות התהפך ב-PDF.
- החילוץ מהטקסט (מרצים, תדירות) מייצר הצעות בלבד. הוא לא מייצר מאפיינים סופיים.
- `split_rule` תלוי במודל השיעורים (מסמך 02).
